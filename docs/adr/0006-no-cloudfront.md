# ADR-0006: CloudFront を作らない

- **ステータス:** 採用（当初の計画から変更）
- **日付:** 2026-08（Phase 5）
- **関連:** [ADR-0005](0005-no-vpc.md)、`docs/spec-architecture.md` §2.6、`docs/roadmap.md` Phase 5-4

## 背景

計画（`spec-architecture.md` §2.6）では、CloudFront と S3 で「ゲームクライアントとアップデートファイルの配信」を行う想定で、ロードマップの Phase 5-4 に入っていた。Phase 5 でマルチリージョン化を終えた段階で、何を配信するのかを確かめた。

| 配信の候補 | 実態 |
|-----------|------|
| Unity クライアント本体 | 作っていない。このプロジェクトの焦点はインフラの品質で、ゲームの完成度ではない |
| ゲームサーバーのバイナリ | GameLift Build として S3 から各インスタンスへ配られる。CloudFront を通らない経路で、CDN を挟む余地がない |
| Web のフロントエンド | ない。クライアントはネイティブアプリで、API は REST |
| API のレスポンス | プレイヤーごと・時刻ごとに変わる（マッチの状態など）ので、キャッシュできない |

## 検討した選択肢

| | 案 | 評価 |
|---|----|------|
| A | 計画どおり CloudFront + S3 を作り、ダミーのファイルを置く | 不採用 |
| B | API Gateway の前に CloudFront を置く | 不採用 |
| C | **作らない** | 採用 |

- **A**: 作ることはできるが、確かめられるのは「空の箱が中身を返すこと」だけになる。オリジンの設計、キャッシュの戦略、無効化の運用といった CloudFront の難しいところには触れない。動いていないものを構成図に足すと、かえって説明しにくくなる
- **B**: 入口を 1 つにまとめたり、WAF を掛けたりはできる。ただしレスポンスはキャッシュできず、レイテンシーによる振り分けは Route 53 で済んでいる（[ADR-0002](0002-region-local-tickets.md)）。CloudFront のオリジンはリージョンごとに固定なので、セッションアフィニティのためのリージョン固有ドメインとも組み合わせにくい

## 決定

**案 C を採用する。CloudFront のモジュールは作らない。**

判断の基準は VPC を作らなかったとき（[ADR-0005](0005-no-vpc.md)）と同じで、使い所がないものは作らず、検討したうえで不要と判断したことを記録する。

## 結果

### 良い点

- 中身のないリソースの費用と、保守の手間がかからない
- 構成図に載っているものは、すべて実際に動いて役割を持っている

### 悪い点・残るリスク

- **CDN の設計を見せる機会がない。**
- **必要になる条件:** Unity クライアントやアップデートのパッチを配るとき。オリジンは S3 にし、Origin Access Control で S3 を CloudFront からしか読めないようにする。証明書は us-east-1 に作る必要がある（CloudFront は us-east-1 の証明書しか使えない。リージョナルな API Gateway は同じリージョンの証明書を使うので、扱いが逆になる）。Route 53 と ACM の Terraform はすでにあるので、作るのに大きな手間はかからない
