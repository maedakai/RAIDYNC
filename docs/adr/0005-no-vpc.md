# ADR-0005: 自前の VPC を作らない

- **ステータス:** 採用（当初の計画から変更）
- **日付:** 2026-07-22（Phase 4）
- **関連:** [ADR-0004](0004-gamelift-managed-ec2-spot.md)、[ADR-0006](0006-no-cloudfront.md)、`docs/spec-architecture.md` §2.1

## 背景

計画の段階（`spec-architecture.md` §2.1）では、VPC を作る想定だった。CIDR 10.0.0.0/16、パブリックとプライベートのサブネットを 2 つずつ、NAT Gateway を AZ ごとに 1 台という構成で、ロードマップの Phase 1 に 3 日を割り当てていた。

この計画は「AWS のインフラなら VPC を切るもの」という一般論から立てたもので、実際の構成から導いたものではなかった。Phase 4 で AWS dev を組む段階で、実際の構成と照らし合わせた。

| 部品 | VPC との関係 |
|------|-------------|
| Lambda | DynamoDB・GameLift・Cognito をすべてパブリックなエンドポイントで呼ぶ。VPC の中にしかないリソースを呼ぶ必要がない |
| GameLift Managed EC2 | GameLift が管理する VPC で動く。自前の VPC には置けない |
| DynamoDB / Cognito / API Gateway | マネージドサービスで、VPC に入れるものではない |
| RDS / ElastiCache | 使っていない |

## 検討した選択肢

| | 案 | 評価 |
|---|----|------|
| A | 計画どおり VPC を作り、Lambda を中に入れる（NAT Gateway 経由で外に出る） | 不採用 |
| B | VPC を作り、NAT Gateway の代わりに VPC エンドポイントで DynamoDB などへ閉じた経路でつなぐ | 不採用 |
| C | **VPC を作らない** | 採用 |

- **A**: Lambda を VPC に入れると、外のサービスを呼ぶのに NAT Gateway が要る。計画どおり AZ ごとに 1 台なら 2 台で月 $60 前後の時間課金が、トラフィックと関係なくかかる。月 $200 の予算の 3 割にあたり、得られるものは何もない
- **B**: DynamoDB のゲートウェイ型エンドポイントは無料だが、GameLift と Cognito はインターフェース型のエンドポイント（AZ ごと・時間課金）が要る。閉じた経路が必要な理由がないのに、費用と構成の複雑さだけが増える

## 決定

**案 C を採用する。自前の VPC は作らず、Terraform にも VPC モジュールを置かない。**

「IaC のカバー率 100%」とは矛盾しない。カバー率 100% は「存在するすべてのリソースが Terraform の管理下にある」という意味で、「計画にあったものをすべて作る」という意味ではない。

## 結果

### 良い点

- 置いているだけでかかる費用（NAT Gateway）がない。dev の固定費は、Route 53 のホストゾーン（月 $0.50）程度に収まっている
- Lambda のコールドスタートに、VPC の ENI の準備が加わらない
- 構成が単純で、Terraform のモジュールと権限が 1 つずつ減った

### 悪い点・残るリスク

- **VPC・サブネット・セキュリティグループを設計して見せる機会が 1 つ減る。** それでも、使わないものを作らない判断を優先した
- **通信はすべてパブリックなエンドポイントを通る。** 経路は TLS と IAM の署名で守られているが、「インターネットを経由しない閉じた経路」が要件になった場合は満たせない
- **VPC が必要になる条件:** RDS や ElastiCache のように VPC の中でしか動かないリソースを足すとき（たとえばランキングに Redis を使う）、または閉じた経路がコンプライアンス上の要件になったとき。そのときは、DynamoDB のゲートウェイ型エンドポイントを先に入れ、NAT Gateway は 1 台から始める
