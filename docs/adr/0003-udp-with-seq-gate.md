# ADR-0003: ゲーム通信は UDP にし、信頼性は「古いパケットを捨てる」だけ自作する

- **ステータス:** 採用
- **日付:** 2026-05（Phase 3）
- **関連:** [ADR-0004](0004-gamelift-managed-ec2-spot.md)、`server/internal/game/session.go`、`server/internal/game/sync.go`、`server/pkg/protocol/game.go`

## 背景

クエスト中の 4 人は、ゲームサーバーと位置や行動を送り合う。サーバーは 50ms ごと（20Hz）に全員の状態（`SESSION_STATE`）を配る。この通信には次の性質がある。

- **新しい値が古い値を上書きする。** 50ms 前の座標は、次のパケットで完全に上書きされる。必要なのは「最新が届くこと」で、「全部が順番どおりに届くこと」ではない
- **遅延がそのまま操作感になる。** 1 つのパケットが遅れたせいで、後のパケットまで止まるのは避けたい
- **接続は最大 20 分張りっぱなしで、サーバーが状態を持つ。** そのため API Gateway や Lambda には載せられない。API Gateway も ALB も UDP を通せないので、UDP にするならゲームサーバーへ直接つなぐことになる

## 検討した選択肢

| | 案 | 評価 |
|---|----|------|
| A | WebSocket（TCP） | 不採用 |
| B | UDP + 既製の信頼性ライブラリ（KCP の `xtaci/kcp-go`、ENet、QUIC） | 不採用（必要になったら移行先） |
| C | **UDP + 古いパケットと重複を捨てる仕組みだけ自作** | 採用 |

- **A（WebSocket）**: TCP の上に乗るので、到達保証・順序保証・再送が付いてくる。ただし 1 つのパケットが失われると、再送されるまで後続のパケットも渡されない（Head-of-Line ブロッキング）。20Hz の位置同期では、これがそのまま「カクつき」になる。また、もう上書きされた古い座標のために再送を待つことになる
- **B（既製ライブラリ）**: 順序保証・再送・輻輳制御を丸ごと任せられる。Unity の Mirror が使う KCP Transport と同系で、実績もある。ただし今の要件（位置の同期）に必要なのは、その一部だけだった
- **C（最小限の自作）**: 信頼性の 4 要素（到達保証・順序保証・重複排除・輻輳制御）のうち、位置同期に要る「順序の逆転を無効にする」「重複を捨てる」だけを作る

## 決定

**案 C を採用する。**

- メッセージは共通の封筒（エンベロープ）に入れる。`type`・`sessionId`・`playerId`・`timestamp`・`seq` と、種別ごとに中身が変わる `payload` の組。サーバーは `sessionId` だけでセッションに振り分け、`seq` だけで順序を判定するので、どちらの処理も中身の種別を知らずに済む
- クライアントは `seq` を 1 から順に振る。サーバーはプレイヤーごとに受け取った最大の `seq` を覚え、それ以下のパケットは黙って捨てる

```
送信 1, 2, 3 → 到着 1, 3, 2
  仕組みなし: 座標が 1 → 3 → 2 と、古い位置に巻き戻る
  仕組みあり: 2 は 2 ≦ 3 なので捨てる。座標は 1 → 3 で最新を保つ
```

- サーバーが配る `SESSION_STATE` にもサーバー側で振った `seq` を載せ、クライアントも同じ方法で古いスナップショットを捨てられるようにした
- **あえて作らなかったもの:** 再送（位置は上書きされる）、欠けた値の補完（補間はクライアントの仕事）、輻輳制御（20Hz の固定レート）、ACK
- 中身は当面 JSON にする。読みやすさを優先した。メッセージの型と送信処理（`Sender` インターフェース）を分けてあるので、後から Protobuf などに差し替えられる
- 外部ライブラリは、GameLift Server SDK 以外は入れていない（`net` と `encoding/json` だけ）。依存を増やさないこと自体が目的ではなく、作るものが小さかったので結果的にそうなった

## 結果

### 良い点

- 1 つのパケットが失われても後続は止まらない。常に最新の状態が反映される
- 仕組みが小さく、中身を全部説明できる。単体テストと、ループバックの実 UDP で往復させる統合テストで確かめている
- GameLift のフリートは UDP のポート（7777）を開けるだけで、ゲームサーバーへ直接つなげる

### 悪い点・残るリスク

- **行動（`PLAYER_ACTION`）も届く保証がない。** 攻撃のような一度きりの重要なイベントも、失われたらそれきりになる。直すなら、同じパケットを複数回送るか、そのイベントだけ ACK と再送を付ける
- **再接続すると `seq` が 1 に戻り、全部「古い」と判断される。** 直すなら、接続ごとの ID が変わったときに覚えている最大の `seq` をリセットする
- **JSON は 20Hz には冗長。** 4,000 接続 × 20Hz では帯域が問題になりうる。その場合はバイナリ形式に変える
- **フル信頼性が要件になったら、自作を広げずに KCP などへ移る。** `seq` で捨てる仕組みは、移行先の順序保証に吸収される
- **パケットの送り主を確かめていない。** サーバーが見るのは、封筒の `playerId` がそのセッションの参加者（roster）にいるかだけで、送信元アドレスはパケットが届くたびに上書きする。参加時に提示されたプレイヤーセッション ID は GameLift に報告する（`AcceptPlayerSession`）が、パケットを受け付けるかの判断には使っていない。他人の `playerId` を名乗ったパケットを送れば、その人として扱われうる。直すなら、参加時に検証したセッション ID とアドレスを結び付けるか、パケットに署名を付ける
