# ADR-0001: マッチ成立の排他は、チケットへの楽観ロックで行う

- **ステータス:** 採用
- **日付:** 2026-06（Phase 2 で採用）、2026-11 に補償処理を追加（Phase 6）
- **関連:** [ADR-0002](0002-region-local-tickets.md)、`server/internal/matchmaking/matcher.go`、`server/internal/db/tickets.go`

## 背景

4 人協力のクエストに参加するため、プレイヤーはマッチ待ちのチケットを発行する。マッチを成立させる処理は、次の条件の中で動く。

- **待ち時間が API の制限より長い。** マッチ待ちは最大 60 秒かかるが、API Gateway は 29 秒、Lambda は 30 秒で打ち切られる。そのためリクエストの中で待ち続けることはできず、チケットを発行してクライアントにポーリングさせる非同期方式にした
- **成立処理を動かす常駐プロセスがない。** 専用のワーカーやスケジューラは置かず、クライアントの `GET /match/status` のたびに Lambda がマッチを試みる。1,000 人が 2 秒ごとにポーリングすると、**同じ待機者を複数の Lambda が同時に自分のグループに入れようとする**
- **DynamoDB には行ロックがない。** `SELECT ... FOR UPDATE` に当たる機能はなく、排他に使えるのは条件付き書き込みとトランザクション（`TransactWriteItems`）だけ

守るべきこと: **1 枚のチケットは、ちょうど 1 つのセッションにだけ割り当てる**（二重割り当ても、一部の人だけが確保される状態も作らない）。

## 検討した選択肢

| | 案 | 評価 |
|---|----|------|
| A | **チケットへの楽観ロック**（`status` + `version` を条件にした `TransactWriteItems`） | 採用 |
| B | 悲観ロック（ロック用アイテムを条件付き Put で取り、作業後に消す） | 不採用 |
| C | 単一の matcher にまとめる（SQS FIFO や EventBridge で定期起動するワーカー 1 つ） | 不採用 |
| D | Amazon GameLift FlexMatch に任せる | 不採用 |

- **B（悲観ロック）**: DynamoDB でロックを作ることはできるが、ロックを取ったまま Lambda が落ちると、TTL か手動の掃除まで解放されない。また大半のポーリングは「4 人そろっていない」空振りなので、競合はちょうど同時に成立する瞬間にしか起きない。めったに起きない競合のために、毎回ロックを取って解放する往復を払うことになる
- **C（単一の matcher）**: 競合そのものがなくなる。ただし常駐するワーカーかスケジューラが必要で、そこが単一障害点とスループットの上限になる。リージョンごとに 1 つ置く必要もある
- **D（FlexMatch）**: 本番のゲームであれば第一候補になる。ただしこのプロジェクトでは、マッチメイキングの整合性を自分で設計すること自体を見せたいので、選ばなかった

## 決定

**案 A を採用する。ロックはセッションではなくチケットに掛ける。**

```
t0  A B C D E が全員 WAITING
t1  Lambda-1 が {A,B,C,D} の 4 枚を、1 つのトランザクションで WAITING → MATCHING にする
      条件: 各チケットの status = WAITING かつ version = 読んだときの値
    Lambda-2 が {B,C,D,E} を同じように確保しようとする
      → B が条件に合わず、トランザクション全体が取り消される（E も WAITING のまま）
t2  勝った Lambda-1 だけが GameLift にセッションを作らせ、Sessions に書く
t3  4 枚を 1 つのトランザクションで MATCHED にする
```

- 取り合っているのは「この 4 人を自分のグループに入れる権利」で、それを表すのがチケットの `status`。セッションは取り合いの**結果**で、作る時点では勝者が 1 人に絞られている。そのため Sessions への書き込みには条件を付けない
- 確保（t1）を先に、GameLift のセッション作成（t2）を後にする。逆にすると、確保に失敗したときに使われないセッションが GameLift に残る
- 負けた側（`TransactionCanceledException`）はエラーにせず、WAITING のまま返す。次のポーリングでまた試みる
- GSI `questId-status-index` は結果整合なので、すでに確保されたチケットが候補に混ざることがある。これも t1 の条件で弾かれるため、GSI の古い読み取りを条件付き書き込みが吸収する形になる

### 途中で失敗したときの補償（Phase 6 で追加）

確保（t1）のあと、セッション作成や MATCHED への更新が失敗することがある。GameLift の呼び出しは DynamoDB のトランザクションに入れられないので、全体を 1 つのトランザクションにはできない。そこで次のように補償する。

- **MATCHED への更新が失敗したとき:** 4 枚を FAILED にしてから、作ったセッションを終了させる（`MarkFailed` → `EndGameSession` → `FailSession`）
- **確保した Lambda が途中で落ちたとき:** MATCHING のまま 40 秒（Lambda のタイムアウト 30 秒に余裕 10 秒を足した値）経ったチケットは、次にポーリングした Lambda が救済して FAILED にする（`rescue`）
- **MATCHED への更新が別の確保と衝突したとき:** `TransactionConflictException` は送り直す（`transactWithRetry`）。1,000 VU の負荷テストで、送り直しがないとチケットが MATCHING のまま止まることを見つけて直した

## 結果

### 良い点

- 常駐するプロセスもロック用のテーブルもいらない。マッチメイキングは Lambda と DynamoDB だけで完結する
- 1,000 VU × 20 回（チケット 20,000 枚、4,968 セッション）の負荷テストで、二重割り当ても MATCHING のまま止まるチケットも 0 だった。DynamoDB の Sessions を集計し、セッションの人数の合計が MATCHED の数と一致することを確かめた（[負荷テスト結果](../load-test-results.md)）

### 悪い点・残るリスク

- **競合は待機者が増えるほど増える。** 空いた席は待ち時間の長い順（`createdAt` の古い順）に埋めるため、全員が同じ古い数枚を取り合う。負けた側も Query と書き込み 1 回分の料金を払う（失敗したトランザクションも課金される）。マッチ成立までの時間が人数とともに伸びる原因の有力な候補
- **チケットではなくプレイヤーの重複は防げない。** `POST /match/request` での「待機中のチケットがすでにあるか」の確認は、GSI を読んでから書く非原子的な処理なので、連打すると 1 人が 2 枚のチケットを持てる。条件付き書き込みはチケット単位なので、1 人が 2 つのセッションに割り当てられうる。直すなら、プレイヤーごとに「待機中のチケット」を表すアイテムを条件付きで書く
- **楽観ロックはリージョンをまたげない。** Global Tables は結果整合のマルチライターで、条件付き書き込みの判定がリージョンごとに行われる。そのため MatchmakingTickets はレプリケーションしない（[ADR-0002](0002-region-local-tickets.md)）
- **GSI がホットキーになる。** 1 つのクエストの待機者が全員同じパーティションキー（`questId`）に集まる。4,000 接続を想定すると書き込みが 1 パーティションキーの上限 1,000 WCU/秒を超える見込みで、既知の限界として残している（[負荷テスト結果 §7](../load-test-results.md)）
