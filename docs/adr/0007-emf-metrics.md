# ADR-0007: メトリクスは CloudWatch EMF でアプリから出す

- **ステータス:** 採用
- **日付:** 2026-09-05（Phase 6）
- **関連:** [ADR-0008](0008-opentelemetry-tracing.md)、`server/internal/metrics`、`server/internal/apigw/respond.go`、`terraform/modules/monitoring`、`terraform/modules/monitoring_dashboard`

## 背景

Phase 6 で、サーバー側のエラーが起きたらメールで通知する仕組みを入れた。そのためには、エラーを CloudWatch のカスタムメトリクスにして、アラームを張る必要がある。

Lambda は 6 関数で、それぞれが両リージョンにあるので、ロググループは 12 個ある。ログはすでに `slog` で JSON にしていた。

## 検討した選択肢

| | 案 | 評価 |
|---|----|------|
| A | CloudWatch Logs のメトリクスフィルタ（ログのパターンからメトリクスを作る） | 不採用 |
| B | **EMF（Embedded Metric Format）。アプリが決まった形の JSON ログを出し、CloudWatch がそれをメトリクスにする** | 採用 |
| C | アプリから `PutMetricData` API を直接呼ぶ | 不採用 |

| | A. メトリクスフィルタ | B. EMF |
|---|---|---|
| 変換ルールの置き場所 | CloudWatch 側（Terraform） | アプリ側（Go のコード） |
| アプリの変更 | 不要（今の JSON ログにそのまま当てられる） | 必要（`_aws` ブロックを含む形で出す） |
| 定義の単位 | ロググループごと | コードの 1 か所 |
| 関数を足したとき | フィルタを足す必要がある。**足し忘れると、その関数のエラーは検知されない** | 何もしなくても乗る |
| ディメンション | 付けにくい | アプリの持つ情報から自由に付けられる |

- **A**: アプリを変えずに済む。ただし 12 個のロググループそれぞれにフィルタの定義が要り、関数を増やすたびに Terraform を追随させる必要がある。「足し忘れた関数のエラーは検知されない」というのは、アラートの仕組みとして致命的だと判断した
- **C**: 呼び出しのたびに API を往復するので、Lambda の応答が遅くなり、API 呼び出しの料金もかかる。EMF はログを書くだけで、送るのは Lambda のログの仕組みが非同期でやってくれる

## 決定

**案 B を採用する。** 決め手は、人の注意力に頼る部分をなくせることだった。

- **出す場所は 1 か所にまとめる。** API の 5xx は、すべてのハンドラーが通る `apigw.Error` から出す。EMF の組み立ては、どこにも依存しない最下層の `internal/metrics` に置き、`apigw`（API の応答）と `matchmaking`（マッチの計測）の両方から使う
- **メトリクス名は、測る量の種類の数だけにする。** 関数ごとの区別はディメンションでつける

| Namespace | メトリクス | ディメンション |
|-----------|-----------|---------------|
| `RAIDYNC/Handlers` | `HandlerError` | `[FunctionName]` と `[FunctionName, ErrorKind]` |
| `RAIDYNC/Matchmaking` | `MatchFormed`、`MatchWaitTime` | `[PartySize]` と `[QuestID, PartySize]` |
| `RAIDYNC/Matchmaking` | `MatchTimeout` | `[QuestID]` |

- **ディメンションのセットは粗い方と細かい方の 2 段にする。** EMF は宣言したセットの粒度でしかメトリクスを作らず、CloudWatch のアラームは複数のメトリクスを合算する検索式（`SEARCH`）に張れない。そこで、粗い方（`FunctionName` だけ）にアラームを張り、細かい方（`ErrorKind` 付き）で原因を切り分ける。アラームを粗い方に張るので、新しいエラーの種類が増えてもアラームを足す必要がない
- **アラームは lambda モジュールが出す関数名の一覧から `for_each` で作る。** 関数を足せば、アラームも自動で増える。5 分間に 1 件以上で SNS からメールを送る。EMF はエラーのときしかデータを出さないので、`treat_missing_data = notBreaching` にして、鳴った後に OK へ戻れるようにした
- **クライアント起因のエラーは数えない。** 4xx や、期限切れの JWT は、サーバーが正しく拒否している正常な動作なので `HandlerError` に入れない。authorizer では、`golang-jwt` の既知のエラーに当てはまればクライアント起因とし、当てはまらない未知のエラーはサーバー起因として数える（見逃さない方を優先する）

## 結果

### 良い点

- 関数を足しても、監視の設定を足す必要がない
- アプリが持つ情報（マッチの人数、待ち時間、クエスト）をそのままメトリクスにできた。負荷テストでは、マッチの成立数と待ち時間をダッシュボードで見た
- 通知の経路は `set-alarm-state` でアラームを強制的に鳴らして確かめた（実際にエラーを起こす必要はない）

### 悪い点・残るリスク

- **監視の責任がインフラからアプリに移る。** EMF の出力を壊しても、ログは普通に出るのでテストも `terraform plan` も気づかない。実際、`_aws.Timestamp` を RFC3339 の文字列にすると（正しくはエポックミリ秒の数値）、メトリクスだけが黙って作られなくなる。EMF の形は単体テストで確かめている
- **`ErrorKind` はエラーメッセージから機械的に作る**（`"ticket lookup failed"` → `ticket_lookup_failed`）。引数を増やさずに全箇所へ適用できる代わりに、メッセージの文言を直すとディメンションの値が変わり、CloudWatch 上は別のメトリクスになる
- **ログのレベルを絞ると、メトリクスも消える。** マッチの成立は INFO で出しているので、ログの出力を WARN 以上に絞ると、マッチ系のメトリクスが作られなくなる。この注意は `internal/metrics` のコメントに残した
- **値の種類が際限なく増えるものをディメンションにしてはいけない。** `err.Error()`（リクエスト ID を含む）やリクエスト ID をディメンションにすると、メトリクスが際限なく作られ、料金も際限なく増える。今のディメンションは、最悪でも 1 リージョンあたり 15 メトリクス程度に収まる
- **アラームはリージョンごとに作る。** CloudWatch のメトリクスとアラームはリージョンの中で閉じているので、両リージョンの合計に張るアラームは作れない。同じものを 2 セット作っている
