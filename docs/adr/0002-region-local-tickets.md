# ADR-0002: MatchmakingTickets はリージョンごとに独立させ、セッションアフィニティで補う

- **ステータス:** 採用
- **日付:** 2026-08（Phase 5）
- **関連:** [ADR-0001](0001-optimistic-lock-matchmaking.md)、`terraform/modules/dynamodb`、`terraform/modules/dynamodb_tickets`、`server/internal/apigw/endpoint.go`、`terraform/environments/dev/dns.tf`

## 背景

Phase 5 で ap-northeast-1（東京）に加えて us-east-1（バージニア）を立て、Route 53 のレイテンシールーティングでクライアントを近いリージョンの API Gateway に振り分けることにした。データは DynamoDB Global Tables でリージョン間に複製する。

テーブルは 4 つある。

| テーブル | 中身 | 寿命 |
|---------|------|------|
| Players | プレイヤーのプロファイル | 永続 |
| Sessions | ゲームセッションの状態 | 最大 20 分 |
| MatchHistory | マッチの結果 | 永続 |
| MatchmakingTickets | マッチ待ちのチケット | 最大 90 秒（TTL） |

全部を Global Tables にするのが一番素直に見える。しかし MatchmakingTickets は、楽観ロックで「1 枚のチケットを 1 回だけ WAITING → MATCHING にする」ことでマッチの正しさを保っている（[ADR-0001](0001-optimistic-lock-matchmaking.md)）。Global Tables には次の性質がある。

- **どのリージョンにも書ける（マルチアクティブ）。** 主従はなく、読み取り専用のレプリカではない
- **同じ項目への同時更新は、後に書いた方が勝つ（last writer wins）。** 負けた方の書き込みは、エラーにならずに消える
- **条件付き書き込みとトランザクションは、リージョンの中でしか判定されない。** 東京で `status = WAITING` を確かめて書いても、同じ瞬間にバージニアで同じチケットを確保できてしまう

つまり MatchmakingTickets をレプリケーションすると、**1 人のプレイヤーが東京とバージニアで別々のセッションにマッチされうる。**

## 検討した選択肢

| | 案 | 評価 |
|---|----|------|
| A | 4 テーブルすべてを Global Tables にする | 不採用（マッチの正しさが壊れる） |
| B | MatchmakingTickets だけ一方のリージョンに置き、両リージョンの Lambda がそこを読み書きする | 不採用 |
| C | **MatchmakingTickets はリージョンごとに独立した別のテーブルにする** | 採用 |

- **B（チケットを 1 か所に集約）**: 待機列が世界で 1 つになり、楽観ロックもそのまま効く。ただしバージニアの Lambda は 1 回のポーリングごとに太平洋を往復する。さらに、東京のプレイヤーとバージニアのプレイヤーが同じセッションにマッチされうる。その場合どちらかが 150ms を超える往復時間でアクションゲームを遊ぶことになり、マルチリージョンにした意味がなくなる。東京が落ちるとマッチメイキングが全リージョンで止まる点も残る
- **C（リージョンごとに独立）**: 待機列がリージョンごとに分かれる。後述のとおり、これはデメリットでもあり目的でもある

## 決定

**案 C を採用する。** Players / Sessions / MatchHistory は Global Tables にする（`modules/dynamodb`）。MatchmakingTickets はレプリケーションせず、各リージョンに独立したテーブルを 1 つずつ置く（`modules/dynamodb_tickets`）。

テーブルを分けると、別の問題が出てくる。チケットを発行したリージョンと、ポーリングが届くリージョンが食い違うと、チケットが見つからず 404 になる。Route 53 の振り分けは DNS の TTL やヘルスチェックの結果で変わりうるし、ポーリングは最大 70 秒続くので、途中で行き先が変わる機会は何度もある。Phase 5 の実機検証で、東京で発行したチケットをバージニアの API に問い合わせると 404 になることを確かめた。

そこで**セッションアフィニティ**を入れた。

```
POST https://api.raidync.com/match/request          ← Route 53 がレイテンシーで東京を選ぶ
  → {"ticketId": "...", "endpoint": "https://apne1.api.raidync.com", "region": "ap-northeast-1"}

GET  https://apne1.api.raidync.com/match/status/{id} ← 以降は応答の endpoint に固定する
```

- Route 53 の役目は、最初の入口を決めることだけにする。`match/request` の応答で、そのリージョン専用のドメイン（`apne1.` / `use1.`）を返す。クライアントは、マッチが終わるまでその宛先を使い続ける
- **どの API を固定するかは、触るテーブルがレプリケーションされているかで決まる。** `match/status` と `match/cancel` は MatchmakingTickets を触るので固定が必要になる。`session/end` と `player/history` は Global Tables しか触らないので、どのリージョンに投げても同じ答えが返る
- 返す宛先は環境変数 `API_BASE_URL`（Terraform がリージョン専用ドメインを渡す）から取る。空のときは、リクエストの `requestContext` からリージョン固有の execute-api の URL を組み立てる。Lambda に API の URL を Terraform で渡すと「API Gateway が Lambda の ARN を要り、Lambda が API の URL を要る」循環依存になるため、リクエストから読む経路も残している

## 結果

### 良い点

- 楽観ロックによるマッチの正しさが、マルチリージョンでもそのまま保たれる。マッチメイキングのコードは 1 行も変えていない
- プレイヤーは同じリージョンのプレイヤーとだけマッチするので、同じセッションのメンバー同士の往復時間が短く保たれる
- 一方のリージョンが落ちても、もう一方のマッチメイキングは影響を受けない
- MatchmakingTickets はレプリケーションの書き込み料金（rWCU）がかからない。書き込みが一番多いテーブルなので、効果が大きい
- 実機で確かめた（2026-08）。日本から `api.raidync.com` へのリクエストが東京に振られた（0.13 秒。バージニア固定の `use1.` は 0.57 秒）。応答の endpoint に固定したポーリングは 200 を返し、endpoint を無視してバージニアに投げると 404 になる

### 悪い点・残るリスク

- **待機列がリージョンで分かれる。** 東京に 3 人、バージニアに 1 人いても 4 人組は作れない。ただし待機列を 1 つにすると B と同じく遠いプレイヤー同士がマッチするので、ここは意図したトレードオフ。人の少ない時間帯は、60 秒待った時点で 2 人以上いれば見切りで開始する仕組みと、ソロ開始で補う
- **「1 人 1 チケット」がリージョンをまたいで効かない。** 待機中のチケットがあるかは自リージョンのテーブルでしか確かめないので、両リージョンの API を直接叩けば 1 人が 2 枚のチケットを持てる。普通のクライアントは 1 つの宛先しか使わないが、不正なクライアントは意図的に突ける。直すなら、プレイヤーごとの「待機中」マーカーを Global Tables 側に置くことになる。ただしその判定もリージョンごとなので、完全には防げない
- **クライアントがアフィニティを守ることが前提になる。** 返された endpoint を無視するクライアントは 404 で失敗する。サーバー側で正しいリージョンへ転送する仕組みはない
- **リージョンが落ちたときは、進行中のマッチが失われる。** 固定先のリージョンが落ちると、そのリージョンのチケットは取り出せない。クライアントは入口（`api.raidync.com`）からマッチをやり直す必要がある。Route 53 のヘルスチェックで自動フェイルオーバーできるが、費用（月 $3）のため dev では既定で無効にしている
